定位、能力与采用判断

先回答：它到底是什么？

它是一套关于“如何组织 AI 编程工作”的课程和实践资料，附带一个可复用 Skill，以及少量能直接运行的辅助工具。

我们的结论：把它当作学习资料和项目工作手册来用。核心目标是帮助你理解 AI Agent 怎样工作，并学会为它准备规则、上下文、任务状态和验收反馈。 主题聚焦 Agent 工作流程与 Harness 工程，不是覆盖所有 AI 知识的通识课程，也不是模型训练教程或安装即用的自动开发平台。

一分钟理解：包含什么、何时用、对我有什么用？

我什么时候用？ 想系统理解 Agent 为什么跑偏时读课程；开始持续开发项目时选模板；经常换会话、重复解释、返工时借鉴进度与验收方法。一次性问答不必引入整套流程。
可以扩展什么？ 定制研究或业务模板，接真实测试和完成证据，再按需加入状态校验、中断恢复、自动循环和多 Agent 协作。这些属于二次开发方向。
对我的意义？ 学会给 AI 写清目标、准备资料、记录进度、判断完成；在当前开源研究集中统一来源、能力、证据、边界与交付检查，减少重复调查和换会话后的重复说明。

推荐的采用顺序是：先理解课程 → 挑选必要模板 → 在一个真实任务上验证 → 有明确需要时再扩展自动化。 不需要先安装整个仓库才能从中受益。

能直接干活的部分

最小生成器读项目清单，建立五个文件。Node 评分器读取固定文件名，检查规则和字段；HTML 工具把评分变成可阅读报告；结构 benchmark 检查工具自己的生成链路和评估用例结构。另有 Bash 审计器，按更广的文档和环境规则检查仓库。

这些工具无需模型 API 就能运行。宿主 AI 的作用是理解你的任务、调整这些文件、实施业务代码和解释结果。工具没有隐藏的业务理解引擎，Skill 也不是一个独立运行的智能体。

为什么可能有效？

模型每次工作的上下文、目标和反馈都影响结果。把项目知识写入文件可以减少重新解释；把大任务拆成可验收的小项可以降低范围漂移；统一验证可以更早暴露失败；交接可以减少跨会话重复劳动。这是工程流程改善的合理机制。

实际收益仍要测量。课程里的示意对照、预填评分、模拟数据都不能直接推算你能省多少时间。更强的规则可能增加启动、维护和运行成本，简单任务未必值得使用整套结构。

适用与不适用

情况 采用建议 观察指标
多天开发一个产品，经常换会话 从最小五文件开始 恢复时间、重复解释次数
已有仓库持续修复、重构 加基线检查和明确修改范围 回归数、返工次数
批量迁移或补充验证 先把任务拆成独立验收项 每项完成率、人工介入、总成本
多角色协作 先分配文件/模块归属，再接独立检查 冲突数、集成失败率
一次性问答或很小的脚本 只保留必要规则 流程维护时间是否超过收益
尚未确定产品方向 先记录决策与探索结果 是否过早固定了错误需求
需要现成智能知识库 不把教学应用当成成品 模型、解析、检索、权限与数据可靠性缺口

对当前研究集的具体意义

当前研究集已经有项目编号、清单、模板、首页生成与检查脚本。这本身已经具备部分 Harness 思路，不必再照搬一套英文文件才能“合格”。

适合借鉴的三个改进点是：

  1. 每项研究定义完成标准：版本、能力清单、实际验证、限制、来源、阅读入口。
  2. 研究中保留简短状态：已核对哪些模块、哪些未运行、下一步是什么。
  3. 完成前调用已有清单检查，并把链接和网页显示检查加入统一入口。

这些是针对本研究集的建议，本次没有把上游 Skill 安装到全局，也没有用上游模板覆盖现有规则。

怎样评价它的价值？

学习价值高：把零散经验组织成清晰体系。模板价值高：可快速形成项目的启动和交接约定。工具价值集中：生成和结构检查实用，但范围有限。生产系统价值需要二次开发：可靠调度、权限、持久化、真实验收与并发控制仍需补齐。

建议以“是否减少返工和人工介入”评价采用结果，而不是以“添加了多少文档、结构分有多高”评价。

证据与运行范围：架构、能力矩阵、验证记录。

底层架构与机制

1. 实际软件边界

你 / 编程 Agent
  ├─ 读取课程与 Skill → 决定工作方式
  ├─ 调用 create-harness.mjs → 向目标项目写五个文件
  ├─ 在目标项目实现功能 → 此过程由宿主 Agent 完成
  ├─ 调用项目检查入口 → 执行目标项目真正的验证命令
  └─ 更新状态、证据与交接 → 下一次继续

结构分析工具
  ├─ validate-harness.mjs → 读文件 → 规则匹配 → 分数与退出码
  ├─ render-assessment-html.mjs → 同一评分 → HTML
  ├─ run-benchmark.mjs → 自检 + 目标评分 + eval 结构检查
  └─ tools/audit-harness.sh → 独立 Bash 规则集 → PASS/FAIL/WARN

仓库没有统一服务端、独立 Agent 主循环或通用模型客户端。上图中的业务实现和真正验证属于宿主与目标项目，而非评分脚本。

2. 脚手架如何生成

create-harness.mjs 调用 harness-utils.mjs：

  1. 解析参数；默认目标为当前目录，默认入口为 AGENTS.md。
  2. 扫描文件并识别根 package.json 或其他技术栈标志。
  3. 识别包管理器；读取现有 scripts 或采用语言级默认命令。
  4. 通过字符串替换填充规则模板；复制固定功能、进度和交接模板。
  5. 使用命令列表生成 Bash init.sh；已有文件默认跳过。
  6. 打印生成情况。这一步不安装目标依赖，不运行目标测试。

Node 路径会选取 check、typecheck、type-check、lint、test、build 中存在的项。未知项目得到提示占位命令；Python 采用 pytest 与 compileall，但没有测试时退出码 5 被接受。

模板生成不是语义分析：不会读取产品需求后自动拆出正确功能，也没有适配复杂 monorepo 的工作图。

3. 五维评分的确切含义

五个维度为 Instructions、State、Verification、Scope、Lifecycle。每维 5 个检查，共 25 个；大部分是文件存在、关键短语、结构行、JSON 字段类型检查。

公式：

单维分数 = max(1, round(通过条数 / 5 × 5))
总分 = round(五个维度分数之和 / 25 × 100)
默认通过线 = 70

因此空目录最低也是 20/100，而不是零。满分表示这些结构规则全部命中，不代表业务功能正确。

读取范围主要是根目录中的 AGENTS.md / CLAUDE.md、feature_list.json / feature-list.json、progress.md、session-handoff.md、init.sh。它不会遍历整个项目检查所有验收依据。

关键限制：

  • JSON 仅检查 features 数组及 id/name/description/status 字符串等基础条件。
  • 随附 schema 中的 status 枚举并未被评分函数执行。
  • dependencies 的存在不代表依赖已满足。
  • “有 Evidence 字样”不代表实际跑过验证。
  • 英文关键短语与约定文件名影响分数；中文或等效自定义命名可能低估结构。

本轮实测见 verification-results.json：无业务代码模板 100/100，改成任意状态字符串后仍为 100/100。

4. 结构 Benchmark 与业务 Benchmark 分开看

Skill 的 run-benchmark.mjs：

  • 临时创建虚构 package.json；
  • 调用生成器；
  • 对生成文件进行结构评分；
  • 检查 evals.json 是否有至少 10 个案例、名称是否覆盖某些类别、字段是否齐全；
  • 对目标项目评分，生成 JSON 和可选 HTML。

它没有让模型执行 10 个案例，也没有运行虚构 package.json 里的 tsc/vitest/build。其自检证明生成器和结构检查链路工作，不证明生成的命令可运行。

P06 的 scripts/benchmark.sh 是另一套工具：拷贝样本、估算分块、搜索关键词；没有调用 TypeScript 服务类。不能把两种 benchmark 当成真实 Agent 效果评估。

5. 为什么文档约束与执行约束不同？

“完成前必须测试”写在规则里，是行为约定；进程返回失败、CI 拒绝进入下一步，是执行关卡。生成的 init.sh 能在命令失败时停下，但前提是：

  1. 宿主确实执行它；
  2. 命令能覆盖真实验收条件；
  3. 命令的退出码正确；
  4. 检查结果对应当前修改版本。

当前工具没有把这四点构成不可绕过的统一控制层。后续扩展应围绕这条链路，而不是增加更多同义规则。

6. 文件状态如何形成“记忆”

功能清单记录“当前任务是什么”；进度记录“最近发生了什么”；交接记录“下一步应做什么”；Git 记录“代码如何变化”。下一轮必须主动读取它们，才能获得连续性。

它们不自动等同于聊天记忆、语义检索或数据库事务。多个 Agent 同时改 JSON 或 Markdown 时，仍需归属、锁、冲突处理和恢复规则。仅把文件写到磁盘不足以保证并发一致性。

结构评分为何容易误解？

scoreHarness 主要做关键词和文件检查。虽然它筛选 Markdown 的标题、列表、表格等结构，减少在普通散文里堆关键词的情况，但并未判断规则是否可执行、证据是否真实、业务行为是否正确。

更具体的限制包括：

  • 使用英文标题/短语；等效中文工作规则可能得低分。
  • 只读取预先列出的根文件；课程里常用的 claude-progress.md 不在 Node 读取候选中。
  • JSON 验证没有使用随附 JSON Schema；status 枚举、依赖合法性和完成证据约束没有闭环。
  • 任务清单为空时，基础数组 every 检查不会要求至少一条功能。
  • 生成脚本和评分器共享相同模板约定，容易形成“自己生成的模板自己评满分”。

应该把分数用于“提醒缺少哪些组织结构”，不用于证明“这个 Agent 值得完全托管”。

示例应用中的实现缺口

问答与检索

qa-service.ts 中预设多个答案模式；按空格分词、字符串包含计分，取前两条引用。confidence 由是否存在引用决定，值为 0.85 或 0.3。没有真实模型 API、embedding 或向量索引。

索引一致性

indexing-service.ts 的单文档索引分支写 chunks 和文档状态，但没有像批量分支一样更新 index-meta；批量路径依据已存在 ID 跳过，没有内容 hash 失效判断。这些是源码观察，本轮未启动 GUI 验证用户可见表现。

持久化

persistence-service.ts 的“atomically”注释对应直接 writeFileSync，缺少临时文件替换、锁或事务；原文件备份也以 filename 为目标。进一步产品化前应处理崩溃中断、并发写入、同名文件及删除后的引用一致性。

验证工具本身

cleanup-scanner.sh 的缺失正文计数在管道 while 子 shell 中增加，最终总数没有获得这一变化；发现问题的分支也没有以非零退出码终止。本轮使用专门样例复现了“输出缺失却 CLEAN”和“ISSUES FOUND 但 exit 0”。

benchmark.sh 使用 python3 time.time 产生浮点数，再交给 Bash 整数运算计算时间，存在运行失败风险；此问题仅做源码判断，未运行该脚本。

图式编排不是现成自动化平台

L14 Python 文件 中：

  • 模型适配器会直接抛出未实现异常。
  • 测试通过依据是代码中存在 def test 字符串。
  • 评审依据是文本中包含 approved；不是严格结构化结果。
  • merge 节点仅打印，不执行提交或合并。
  • 内存检查点不是磁盘数据库；文件注释中对进程死亡恢复的表述超出该选择的能力。
  • attempts 声明为累加字段，但节点未返回增量。
  • 失败回到 implement 时，实现节点只读取 requirements，没有使用 review 内容进行针对性修复。
  • 路由遇到非 fail 字符串就进入 merge；生产实现应对未知状态显式处理。

这不妨碍它说明节点与路由概念，但需要重新设计真实工具执行、可恢复状态、错误分类和停止条件。

模板之间存在多种协议

课程功能表偏向 verification_steps、passes 等验收字段；Skill 表使用 status/evidence/dependencies。独立 Bash 审计偏向 PROGRESS.md、Makefile、锁文件和反馈文档；Node 评分偏向 progress.md、init.sh 与固定英文标题。

同样名为 init.sh 的文件也不完全一致：资源库版本会先切换到脚本目录并可选启动应用；生成器版本不切换目录，只执行选择的命令；P06 版本主要安装、类型检查、构建和文件存在检查。选择模板时应按行为评估，不能仅凭文件名互换。

证据范围与未验证内容

本轮没有做真实模型对照试验，没有运行长期自动循环，没有启用外部连接器或权限引擎，没有启动 Electron 界面，也没有构建整个上游网站/PDF。跨语言课程只做目录、字节与哈希核对及核心中英文抽样，不评价每种翻译质量。

方向一：从“检查文件”到“检查行为”

保留当前结构检查作为入门诊断，增加可执行的业务验证契约：

  • 每项功能有用户行为、输入、预期结果、验证命令。
  • 证据至少记录任务 ID、代码版本、执行时间、命令、退出码和必要产物。
  • 完成状态与本次代码版本绑定，修改后使旧证据失效。
  • 检查器不可只信任 Agent 自己填写的“通过”。

先做一个能捕获真实回归的检查，比增加十条泛化规则更有价值。

方向二：统一状态管理

最小版本仍可用 JSON，但应校验任务 ID 唯一、依赖存在、无依赖环、状态迁移合法。多个工作者参与后，建议增加任务归属、乐观锁/版本号或数据库事务。

持久化应区分三种数据：当前可恢复状态、追加的事件日志、体积较大的验证产物。进度说明给人阅读，结构化状态给程序路由，不要让自由文本同时承担所有角色。

方向三：把循环接成真实系统

建议按以下顺序实现：

  1. 接入一次真实模型/Agent 调用，明确输入输出。
  2. 接入受控项目工具与实际验证。
  3. 给 Checker 独立验收标准，优先使用确定性检查。
  4. 分类失败：代码问题、环境问题、需求不清、权限问题。
  5. 失败回传完整证据；限定轮数、时间和总费用。
  6. 把检查点写到持久存储；重启不能重复做不可逆动作。
  7. 只有确实需要时再增加并行节点和人工审批节点。

这些需要外部执行环境。改写提示模板不会自动获得调度、进程恢复或事务能力。

方向四：将示例知识库产品化

要得到真实知识库，应另行增加：

  • 文档解析：PDF、Office、编码识别以及需要时的 OCR。
  • 检索：分词、embedding、混合检索、重排和权限过滤。
  • 生成：模型适配、引用约束、无证据回答策略。
  • 数据：增量失效、删除传播、事务、备份与恢复。
  • 验收：固定问答集、引用正确性、无答案案例、延迟与费用。

不要把“多接一个模型 API”当成产品化完成；当前检索、索引和数据一致性也需要补齐。

方向五：用于你的项目研究流程

可从现有研究集上做一个轻量模板，不新增复杂平台：

阶段 输入 产物 验收
固定版本 仓库 URL commit、许可、文件索引 来源明确、哈希匹配
能力盘点 源码和说明 输入/产物/机制/边界矩阵 宣称与实现分开
复现 明确的功能路径 环境、步骤、日志 实测和未测分开

本轮新建的子项目已按这个思路组织研究产物；它不是在工作区安装了一套通用 Agent 系统。

如何做真实收益对照？

从同一代码起点选 3–5 个有明确验收的小任务，尽量保持模型、工具、时间预算和任务难度一致。比较采用前后：

  • 任务成功率：按独立验收计算，不按 Agent 自述。
  • 人工介入次数和总时间。
  • 返工、回归和错误完成次数。
  • 端到端耗时与模型/运行费用。
  • 换会话后的恢复时间。
  • 规则和状态维护成本。

样本小的时候只作为试点观察；不要从一两个成功案例宣称稳定提升百分比。扩展顺序建议为：真实验收 → 准确状态 → 可靠恢复 → 自动循环 → 按需并行。
