# witr 全景理解图生成记录

生成方式：内置 image_gen，非 CLI。用途：本研究子项目的单张综合信息图。

## 最终提示词

制作一张可保存、可放大阅读的高清中文技术信息长图（infographic-diagram），概括开源工具 witr。单张完整竖版海报，建议 2400×3600 或相近高分辨率，约 2:3 比例。信息量较大，保证所有文字清晰、逐字正确、无缺字乱码。不要画照片、人物、电脑插画、假截图或无意义装饰；以专业信息设计、精确中文排版、流程箭头、模块和四列对照表组织。白色/极浅蓝底，深海军蓝文字，青绿色强调，局限提示少量琥珀色。现代中文黑体，命令用等宽字体。每区编号、标题和正文层级明确。均衡留白但内容要充分，任何文字不得裁切。八个编号区块加底部来源。图中区分“已有能力”“扩展建议”“价值判断”，不要将建议误写为现成功能。

标题（最大字）：“witr 全景理解图”
副标题：“Why is this running? · 运行来源诊断工具”
定位条：“Go 编写 · 跨平台 CLI / TUI · 系统信息采集 + 关联规则 + 统一展示”
核心判断醒目展示：“底层查询能力多已存在；增量价值在自动关联、跨平台适配和排障体验。”

01 “能力是什么？”
六个简洁分组，保留以下文字：
“查询对象：进程名称 / PID / 端口 / 文件 / 容器”
“追溯来源：父进程链、终端、系统服务、进程管理器”
“补充上下文：启动命令、用户、时间、目录、Git、容器”
“资源信息：CPU、内存、部分 I/O、线程与句柄”
“诊断线索：特权运行、公开监听、高内存、僵尸进程等”
“范围：操作系统运行对象；不理解项目待办或 AI 任务语义”

02 “底层怎样工作？”
水平或纵向五步箭头：
“输入对象 → 定位 PID → 读取状态与 PPID → 识别启动来源 → 汇总报告”
下方正文：
“沿父进程逐级向上查找，再关联服务、容器和工作目录。”
“读取系统数据 + 调用原生 API + 解析现有命令；不只是命令别名。”
“示意：3000 端口 → node → 终端启动 → demo 项目”

03 “支持系统与运行机制”
四列或四张同等大小的卡片，每个平台完整包含下面内容：
“Linux”
“采集：直接读取 /proc”
“进程：stat / cmdline / cwd / environ”
“网络：网络表 + socket inode + fd”
“服务：cgroup + systemd D-Bus”
“特点：功能最完整；容器详情可能调用运行时 CLI”
“Windows”
“采集：原生 API + 部分命令”
“进程：ToolHelp32；PEB / 系统查询”
“资源：GetProcessTimes / PSAPI”
“网络：解析 netstat -ano”
“服务：SCM；文件查询：Restart Manager”
“限制：无 Locks 面板、无 TUI 进程操作”
“macOS”
“采集：ps / lsof / sysctl”
“网络与文件：lsof”
“服务：launchd 相关信息”
“扩展指标：可选 libproc（依构建条件）”
“限制：SIP 与权限会影响详情”
“FreeBSD”
“采集：ps / procstat”
“网络：sockstat”
“服务：rc.d 脚本与 PID 文件”
“隔离环境：jail / jls”
“特点：结合现有系统工具进行解析”
该区共同备注：“四平台均有主要查询能力；容器查询需对应运行时工具与权限。”

04 “如何使用？常用指令速查”
清晰两列表格，左列完整等宽指令，右列中文释义，不把所有命令挤成一行：
“witr” | “打开终端交互界面”
“witr node” | “按进程名称查询”
“witr --pid 1234” | “按 PID 查询”
“witr --port 3000” | “查端口占用者”
“witr --file <路径>” | “查文件相关进程”
“witr --container redis” | “查询容器”
下方两行选项：
“输出：--tree 进程树 · --short 简短链 · --json 结构化输出”
“详情：--verbose 扩展信息 · --env 环境变量 · --warnings 提示”
“其他：--exact 精确匹配 · --no-color 无颜色 · --help 帮助”
小提示：“退出码：0 无警告 / 1 有警告 / 2 未找到 / 3 权限 / 4 输入或多匹配 / 5 内部错误”

05 “展现形式与实际效果”
三条：
“CLI：一次查询，一份文字报告或进程树。”
“TUI：终端内交互面板，可浏览进程、端口、容器等。”
“JSON：给脚本或其他界面使用的结构化数据。”
强调框：
“本次研究网页 = 模拟教学演示，不读取本机。”
“真实 Web 界面需另建：网页 → 本地后端 → witr → JSON。”
“实际收益：少切换工具、少核对 PID，更快找到该处理的项目或服务。”

06 “必须理解的边界”
用不夸张的琥珀色点缀，五条：
“当前关系不等于完整历史；进程退出、重新托管会打断线索。”
“文件被打开不等于持有排他锁；Windows 文件查询不等于锁列表。”
“Linux / Windows 基础 CPU 指标为生命周期平均，非瞬时负载。”
“权限、容器和虚拟机隔离限制可见范围；不会自动看穿所有环境。”
“规则提示只是线索；不替代性能剖析、历史审计或故障根因分析。”

07 “对我的意义：如何评价？”
明确标注“针对已有开发工具链的判断”
三行评价不使用虚构评分：
“新增底层能力：较低 —— 与系统接口、现有库重合度高。”
“日常排障价值：取决于使用频率 —— 开箱即用，减少手工关联。”
“研究复用价值：适中 —— 可借鉴平台适配、来源规则与输出组织。”
结论：“定位为诊断工具整合与体验优化；若目标是独特底层能力，可降低研究优先级。”

08 “后期怎样扩展？”
明确标签“以下是二次建设建议”
四个由浅入深层级：
“1 外部集成：调用 --json + 退出码，接入脚本、检查流程。”
“2 真实 Web / AI 工具：增加本地后端或 MCP 包装；不是已验证的官方能力。”
“3 定制识别：proc 扩采集，source 扩规则，pipeline 聚合，output / tui 展示。”
“4 历史监控：另加事件采集、存储、趋势与告警；快照不能补回历史。”
补充：“核心位于 Go internal；直接作为 SDK 嵌入需提取接口。”
“接入真实数据时：限制查询权限，处理环境变量与命令行中的敏感信息。”
