## 一、能力与安全边界

上游定位是菜单栏中的本地 Mac 清理应用，SwiftUI 提供原生界面，Rust 提供扫描和操作引擎。它发现用户选定位置和已知工具位置中的候选项目，展示估算大小、原因与后果，再由用户决定保留或处理。

类别包括开发依赖、构建产物、npm/npx/Corepack/Bun/pip/uv/mise/Cargo/SwiftPM/Zig/Expo/Homebrew 下载/AWS CLI 等已知缓存，以及应用缓存、日志、Python 字节码、Xcode DerivedData、下载和个人大文件。类别间权限、复核与允许操作不同。已知工具缓存也可能因活动、共享文件、目录内容或归属不满足条件而被禁用；测得大小不意味着全部可删。

重复文件检查是用户主动发起的有界过程：比较已经索引的旧/大个人文件建议、验证内容，再复核要保留和要处理的副本。普通扫描不对个人文件内容做全量哈希，也不是全盘去重服务。

源码依据：[根 README](https://github.com/richiemcilroy/chippytea/blob/f245695/README.md)、[scanner.rs](https://github.com/richiemcilroy/chippytea/blob/f245695/core/src/scanner.rs)、[safety.rs](https://github.com/richiemcilroy/chippytea/blob/f245695/core/src/safety.rs)、[duplicates.rs](https://github.com/richiemcilroy/chippytea/blob/f245695/core/src/duplicates.rs)。本轮未实机验证这些清理类别。

## 二、系统与原理

| 层 | 文件或目录 | 作用 |
| --- | --- | --- |
| 原生界面与平台桥接 | `native/Chippytea/`，`EngineBridge.swift` | SwiftUI、菜单栏、扫描位置授权、Finder/Trash、引擎数据和历史界面 |
| 扫描、索引和候选 | `core/src/scanner.rs`、`store.rs`、`recommendations.rs` | 有界发现、SQLite 状态与建议，区分候选与真正可处理项目 |
| 操作前复核 | `core/src/safety.rs`、`cleanup.rs`、`activity.rs` | 检查归属、活动和文件状态，按类别决定允许的操作 |
| 核算与账本 | `core/src/accounting.rs`、`store.rs` | 操作观察窗口、保守空间核算、余额与持久记录 |
| 共用视觉语言 | `native/Chippytea/CoinScene.swift` 与 `site/lib/ink.ts` 等 | 原生和官网采用相同种子绘图思路与角色语言 |
| 网站应用 | `site/` | Next.js/React、SVG/Canvas、CSS、Web Audio、原作示例与歌曲 |

原生数据流可以概括为：选择扫描位置 → 收集与索引候选 → 用户审阅 → 操作前重新验证 → 执行允许操作 → 形成结果记录 → 保守核算 → 更新本地余额与视觉反馈。图形反馈在结果之后，不能反过来替代对结果的核实。

### 计奖不是按估算大小直接相除

`accounting.rs` 先要求操作为永久清理、目标内容完整移除、私有分配可证明、审阅项目存在分配字节，并且容量采样显示可用空间增加。空间计奖受到三个上界约束：可证明的私有分配、审阅分配大小、扣除测得背景增长后的容量增量。条件不足时计奖为零；APFS 共享、快照和其他磁盘活动也会影响游戏计奖，源码没有把它称为精确磁盘节省结论。

累计本次有证据支持的空间与历史余量后，按十进制 **100 MB = 100,000,000 字节** 增加一个 chip，余量继续保留。操作、核算分配、收入和余额在 SQLite 事务中更新，避免同一个观察窗口被重复结算。

**移入 Trash 不建立已恢复空间，也不计奖。** 应用缓存、日志、Python 字节码、Xcode DerivedData、下载与个人文件属于上游说明的审阅/Trash 范围；符合条件且重新验证通过的开发缓存、依赖与构建文件才可能永久操作并计奖。不能为了让动画好看，把所有文件估算大小都转换为奖励。

依据：[accounting.rs](https://github.com/richiemcilroy/chippytea/blob/f245695/core/src/accounting.rs)、[cleanup.rs](https://github.com/richiemcilroy/chippytea/blob/f245695/core/src/cleanup.rs)、[根 README 计奖说明](https://github.com/richiemcilroy/chippytea/blob/f245695/README.md)。这是源码核对结果，不是对本机空间核算的测量。

## 三、风格拆解与复用范围

`ink.ts` 的颜色表提供奶油纸底 `#FAF5EA`、深纸色 `#F1EADB`、卡片 `#FFFDF6`、炭黑 `#33302B`、金黄 `#F2B63C`，并配蓝笔与锈红。纸张、点阵、便签和胶带使产品像生活中的小纸条；正文保持清晰，角色与手写数字承担装饰和成果表现。

`handPath` 的关键不是随机抖动每一个像素，而是对轮廓采样点加入**可复现的种子噪声**，再以二次曲线中点平滑成形。同一 seed 保持相同轮廓，循环三个 seed 形成约 167 ms 一次的线条重绘。SVG 和 Canvas 共用同一个轮廓思路，适合让按钮、卡片、图标、鱼、薯条和数字保持一致。

| 模块 | 可复用能力 | 必须补做的工作 |
| --- | --- | --- |
| `ink.ts`、`art.ts` | 种子墨线、配色、角色与手写字形 | 使用我们的原创形象、品牌语义与可配置 token |
| `InkBox.tsx`、`art.tsx` | 手绘交互控件与 SVG 角色 | 与现有设计系统、键盘和移动交互整合 |
| `draw.ts` | 纸包、薯条、余额的 Canvas 绘制 | 按业务成果设计容器与收藏物，处理缩放和可读文本 |
| `DemoPanel.tsx` | 审阅、模拟结果、收藏动画的一段完整交互 | 替换虚构数据，连接真实业务的完成和核验事件 |
| `chime.ts` | Web Audio 合成短收集声音 | 可关闭声音、按用户手势启动、处理暂停与资源释放 |
| `Karaoke.tsx`、`lyrics.ts`、`sections.ts`、`karaokeScene.ts` | 音频时钟、词级同步、段落表演、点击反馈 | 更换授权音乐、生成并人工校正歌词时间、设计新段落表演 |

源码注明绘图原语来自原生 `CoinScene.swift`；这个跨原生与网页的统一视觉语言比单纯复用一张插画更有参考价值。

### MiniMax 配乐的重新生成

工具位于 `tooling/generate-music.py`。待本地账号有可用音乐接口后，可从仓库根目录执行；示例应换成自己的本地配置路径：

```powershell
python projects/016-chippytea-lab/tooling/generate-music.py --generate --env-file C:/private/.env.minimax
```

过程记录在 `notes/music-generation.json`。只有真实生成与文件处理成功后，才接入本地 `web/audio/research-to-folio.mp3`、HTMLAudio 媒体时间和实际频谱。拒绝与失败状态不能视为生成成功，也不会自动提供合成替代音轨。成功后重新构建，并检查实际播放、暂停恢复与声画同步。

原作 `DemoPanel.tsx` 使用内存中的虚构文件和预设成功结果。默认纸包余额为 854 chips；例如 2.40 GB 的 `target` 清理示例会表现为 24 chips 的增加。这是一段交互说明，不是扫描和存储恢复测试。下载样例只能移入 Trash，不增加奖励。

本地页面复用原作的 `DemoPanel`，提供重置，并将能力说明拆为发现、复核、计奖与原生四个可切换角度。风格实验复用 `FishSvg`、`MugDoodle` 和 `InkBox`，允许切换画笔 seed 和三帧循环。画廊与音乐区保留首页、审阅、结果、歌曲和桥段的原官网截图。

新增任务实验将 015 的研究工作示意为可完成事项：完成一次后绘制薯条进入纸包，数字与可选短音效响应，重复点击已完成项不会再次领，支持重置和导出本轮结果 JSON。Canvas 复用上游 `paintWrap` 与 `paintChip`，任务规则和价值说明由本项目新增。它当前是内存原型，没有连接 015 真实任务，也没有跨设备、账号、后端或持久奖励账本。

### 从重复工作走到真实研究入册

用户进一步要求“日常重复最多的进行分析，用真实场景搭配一个真实的效果看看”。本次没有活动日志、每日次数或工时数据，因此以跨项目覆盖分析重复流程。分析时的快照包含 17 个项目，均登记来源、建立 README 与研究笔记入口，16 个有 Web 入口，15 个登记了存在的封面。先选择的承载案例是：看案例、核对来源与源码、整理能力原理、做展示、登记索引、复核留存。具体快照时间、统计方法与逐项文件证据见 [daily-work-analysis.md](daily-work-analysis.md) 和 [daily-work-evidence.json](daily-work-evidence.json)。这是跨项目覆盖分析，不表示已经测得每天耗时最多；项目随后新增或补全不会改写这份历史快照。

资料与回执页面入口为 `http://127.0.0.1:8977/projects/016-chippytea-lab/?view=research&mode=records`。它读取当前在册项目，选中一个项目后呈现实际资料状态、缺项与依据；点击“核验并入册”后，由本机 Python 服务重新读取文件，而不是由浏览器按钮直接判定成功。这部分是演出所需真实业务连接，主体验仍是上述完整声画舞台。

| 核验项 | 实际规则 | 可以支持的判断 |
| --- | --- | --- |
| 目录与总索引 | 清单 ID/slug 对应目录存在；主 README 生成块与清单一致 | 项目已按仓库结构登记 |
| 来源 | 清单有通过登记格式检查的 HTTPS 源库或参考字段；不访问上游 | 有可追溯的来源字段，不证明源站可达或事实正确 |
| README 与笔记 | README 和至少一份 notes 顶层 Markdown 去掉注释、标题、链接地址及已知模板提示后，达到 100 个非空白字符的粗略阈值 | 有超过空模板的资料量；不判断语义、完整性或质量 |
| 封面 | 未登记是可选项；登记后文件须存在且可读，并记录哈希 | 登记素材存在，不判断画面质量 |
| Web | 未建立入口是可选项；已有 `web/index.html` 须非空，读取入口与 Web README | 有展示入口，不证明资源、交互或浏览器验收通过 |

服务只读取清单项目的固定文件范围与必要顶层 Markdown，不递归扫描个人目录。资料指纹包含该项目清单条目和核验材料的哈希；主 README 使用该项目的索引摘录，避免其他项目修改使全部回执失效。客户端只提交 `projectId`，服务自行决定是否满足条件。

通过后，服务将唯一回执原子保存至 `notes/research-collection.json`，包含 UUID、项目编号、序号、首次保存时间、核验时间、资料指纹和检查依据。每个项目只占一个位置：首次保存增加数量，重复核验不增加，资料变化则更新同一回执。失败时不返回成功；损坏账本被保留并显示错误，不自动清空。入册不会更改 `projects.json` 的研究完成状态，也不保存全部历史修订。

浏览器收到新增回执成功响应后，才让研究卡片在约 1.3 秒内飞入收集册，编号落印、数字增长，并在卡片归位时播放上游 `chime.ts` 合成的约 0.67 秒短声音。这些反馈对应同一次真实保存；重复核验与回执更新不制造新增奖励。声音可关闭或试听，试听不写入回执；减少动态偏好省略飞行与数字渐变，保留文字结果。最终交互实测与截图仍由 [设计验收记录](../design-qa.md) 记录，不能由源码实现直接宣布通过。

静态页面使用构建时的 `web/research-state.json` 只读快照，明确标记未连接本机服务并禁用入册。快照生成脚本仅读取，不创建回执。这样同一页面既能公开展示实际资料，又不会在没有服务器保存的情况下假装完成。

### 歌曲的时间同步与跨域处理

上游歌曲 **Save Your Mac with chippytea** 由 `<audio>` 播放，歌词每个词有起止时间；`sections.ts` 将歌词连续段落归为 intro、chorus、verse、pre-chorus、bridge、last chorus 等区间。`Karaoke` 按 `audio.currentTime` 查找当前词和段落，`karaokeScene` 根据区间编排游鱼、薯条、拍手、强调与点击投放。原官网的 AnalyserNode 检查低频强度变化形成节拍刺激，它没有自动完成整首歌的分镜。

本地 `SONG_SRC` 指向原官网歌曲，不下载音乐归档。跨域媒体通过 `createMediaElementSource` 时可能受 CORS 限制而得到静音，因此本地让远程原曲走 HTML 音频原生播放，跳过音频分析节点，并使用现有 `FALLBACK_BEAT`（0.5 秒）驱动角色节奏。歌词、段落和拖动后的同步继续依据音频真实播放时间；关闭时通过 HTMLAudio 的 `volume` 淡出。**这份适配让远程歌曲走原生播放通道，实际可听与同步仍需浏览器验证；它不是本地对原曲做实时频谱检测。**

词级时间生成方案来自上游：歌词表加 Whisper word timestamps 后执行对齐脚本，生成 `lyrics.ts`。新的歌曲仍需人工校正时间和表演；更换音轨不能沿用原曲时间数据。依据：[site/README](https://github.com/richiemcilroy/chippytea/blob/f245695/site/README.md)、[Karaoke.tsx](https://github.com/richiemcilroy/chippytea/blob/f245695/site/components/Karaoke.tsx)、[sections.ts](https://github.com/richiemcilroy/chippytea/blob/f245695/site/lib/sections.ts)。

本地构建入口为 `tooling/build.mjs`，将 `src/App.tsx`、React 与复用模块打包进 `web/app.js`；上游署名保留于 `app.js.LEGAL.txt` 和 `source-notice.html`。静态服务可以直接消费 `web/`，共享站由仓库 `scripts/build_site.py` 汇总。

完整演出由 `src/Experience.tsx`、`PerformanceStage.tsx` 和 `performanceAudio.ts` 提供，资料操作由 `src/ResearchWork.tsx` 与 `tooling/research_server.py` 提供。构建时先运行 `python projects/016-chippytea-lab/tooling/research_snapshot.py`，再运行浏览器打包和共享站构建；从仓库根目录执行 `python projects/016-chippytea-lab/tooling/research_server.py` 启动服务。Python 服务不调用原生清理引擎，不修改研究清单，只写入本子项目的回执账本。详细操作见 [Web README](../web/README.md)。

`web/upstream.css` 来自当日官网已加载的 [编译样式资源](https://www.chippytea.com/_next/static/immutable/chunks/2mwteocwimcul.css)，对应上游 `site/app/globals.css` 和组件工具类。该资源的发布哈希属于官网构建，不等于研究 commit；本项目另用 `web/style.css` 编写研究布局、任务实验和中文样式，来源也保留在浏览器 `source-notice.html`。

## 六、场景与对我们的价值

首要价值是把功能扩展为完整的动画、音乐与互动场景。业务事件提供真实素材与触发点；演出层组织音频主钟、角色、绘图、字幕、段落情绪、参与动作和收尾。这套组织方式既可用于一次成果，也可用于产品介绍、互动歌曲、课程结课或创作结果。

| 对应已有研究 | 可结合的部分 | 当前价值判断 | 后续验收 |
| --- | --- | --- | --- |
| 015 任务冒险 | 任务事件触发角色、配乐与分段演出 | 用实际成果素材演出，而不是只弹出一个完成提示；接入 015 业务仍需实现 | 业务只结算一次，演出可重复播放；事件和演出成功分别处理 |
| 004 音乐叙事 | 声音作为主时钟、角色演出、段落情绪 | 可形成轻量互动歌曲模板 | 暂停、跳转和重新播放时音画同步，用户手势启动，能退出 |
| 008 字体动效 | 字词高亮、手写数字、字幕节奏 | 可把固定视频效果延伸到可操作字幕与歌词 | 词级数据可编辑，不依赖特定歌曲，移动端字幕清楚 |
| 010 手绘生活产品 | 自有角色、低帧率线条、纸张控件 | 可沉淀统一品牌表达，适合生活化产品 | 新角色与按钮卡片一致，装饰不会遮挡文字和操作 |

传播、习惯完成率、长期留存和付费都还是假设。网站“能玩且有辨识度”可以观察，商业成效不能从源代码或一次体验直接推断。

研究入册是这次可操作的承载案例。最应沉淀的能力是：把一个确定的功能事件编排为有节奏、可参与、能暂停重播的声画段落。统一墨线和角色减少素材断裂，主时钟减少音画漂移，段落脚本组织起承转合；这些是可复用实现。旋律、动作、字幕与业务含义如何匹配仍需创意判断，不能通过复制源码自动获得。资料核验与去重使真实事件可信，但不是本轮重点价值。

## 七、扩展顺序

1. 从当前完整演出抽出业务输入、配乐、主时钟、段落脚本、角色、字幕和交互配置，接入一个真实任务或生成结果。
2. 优先检查完整视听过程：首屏动作是否可见、场景是否随音乐换段、暂停恢复是否同步、重播是否不影响业务数量、手机构图是否清楚。
3. 扩展原创或授权音乐、词级时间编辑、角色表演与场景脚本；处理音轨失败、用户手势启动、退出、资源释放与减少动态效果。预设节拍与频谱检测分别说明。
4. 本机回执已持久保存；需要产品化时再增加撤销、修订历史、账号与多人状态，清理原生工具则另做平台权限、文件操作安全、恢复与引擎测试。

先打磨一段完整声画体验，再观察它是否服务产品表达和用户行动。源码复用能降低绘图与同步的重复工作；长期产品效果与商业结果仍需真实使用验证。
