# 日常重复工作的分析与真实反馈场景

日期：2026-10-02。分析对象是当前研究工作区的项目材料、清单、内容约定和构建脚本。数量及逐项文件证据见 [daily-work-evidence.json](daily-work-evidence.json)。

## 我们反复做的是什么

当前工作区最稳定地重复出现的工作，是**把一个感兴趣的案例，变成以后能回看、比较和采用的研究成果**：看案例与原作效果 → 核对来源和源码 → 整理能力、原理、场景、价值和边界 → 做说明图或可操作展示 → 登记到总索引 → 复核并保存。

这是一项有真实输入、真实文件和真实成果的工作，适合先试 Chippytea 的成果反馈思想。仓库没有全天活动日志、工时或每日操作次数，本次结论表示“在项目间反复出现的流程”，不能据项目数量断言每天花在哪一步的时间最多。

## 真实场景：工作区研究入册

例如今天看完 Chippytea，我们已留下来源、能力原理说明、截图、可操作网页和目录登记。下一步点击“检查并入册”，系统检查这份工作区成果，再生成一张可以打开原作、研究说明和本地展示的收藏卡。

建议交互闭环：

1. 选择一个实际登记的项目，先显示缺少什么和已有成果链接。
2. 检查来源、清单、研究说明、展示入口与代表图。状态由实际检查返回；失败时给出可解决的缺项。
3. 材料条件通过且该版本首次入册时，研究卡从工作区进入书架，编号印记落下，响起一次短声音。
4. 动画结束后留下项目名称、核验时间和三个成果入口；再次检查同一份成果只显示已有记录。
5. 修改成果后可重新检查、更新该卡，不把同一项目的重复点击累计为多张完成卡。

卡片、编号和书架直接对应我们真实积累的研究成果。第一轮只需要一个认真打磨的“归位”动作、一个落印动作和一个短音效；一般阅读、判断和错误提示保持清楚、平静。

## 真实触发条件与计奖边界

建议自动检查的内容包括：项目 ID 与目录对应，源库或参考链接已登记，README 和研究笔记存在且没有关键“待填写”项，网页入口与本地资源存在，封面路径有效，目录索引检查通过。展示操作和内容质量仍按各项目的实际验收记录判断。

自动检查应呈现“材料条件已满足”“浏览器验收待完成”等明确状态。文件存在仅能支持材料完整度；能力是否准确、原作是否被忠实呈现、实际效果是否可靠，需要内容复核和对应实验。入册不改变 `projects.json` 的研究完成状态。

计奖以“项目 ID + 成果版本指纹”去重，服务器先确认保存记录，再返回一次成功反馈。每个项目在书架占一个位置；更新版本替换卡片并保留更新记录。取消、检查失败、刷新、重复点击和单纯打开页面不产生新奖励。使用合成短音效并提供静音，尊重减少动态偏好。

第一轮验收观察四件事：用户能否说清刚入册的成果是什么；能否立即回到来源或展示；失败原因是否可执行；重复提交是否仍只有一张卡。是否更愿意完成研究、是否节省时间，都需要后续实际使用记录。

## 分析来源与复核方法

- 数据清单：[projects.json](../../../projects.json)，本次实际读取 17 条记录；统计不使用线程数量、提交数量或修改时间推算工时。
- 内容规范：[docs/CONVENTIONS.md](../../../docs/CONVENTIONS.md)：规定项目编号、来源、研究目录、登记与检查方式。
- 目录工具：[scripts/projects.py](../../../scripts/projects.py)：检查字段、来源格式、目录、封面和主 README 同步；不访问源站，不证明原生产品可靠。
- 静态构建：[scripts/build_site.py](../../../scripts/build_site.py)：只有存在 `web/index.html` 的项目进入共享展示。
- 研究保存：[docs/RESEARCH_ARCHIVE.md](../../../docs/RESEARCH_ARCHIVE.md)：说明文件快照、版本保留和恢复边界。
- 内容抽查覆盖前 16 项的 README、`notes/research.md` 和 Web 说明；017 作为模板阶段单列。逐项路径、大小、哈希和状态保存在配套 JSON 中，可复查本次材料快照。
