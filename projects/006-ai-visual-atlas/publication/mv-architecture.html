OUR UNDERSTANDING / 创作主体与技术路线分别选择

人物为主、场景为主，都可以选择不同的制作方法。

人物主导：围绕演唱者的风格、情绪与动作安排画面。场景主导：先设计车厢、城市或故事空间，再安排人物进入。两者是创作选择；“分层、整体生成、后做嘴型”等是技术选择，一支 MV 可以按镜头混用。

选择一 · 画面围绕谁

围绕演唱者编排画面

人物负责唱歌和情绪，背景、文字、图形与镜头配合人物及歌词。makevoid 默认路线更接近这种角色主导的分层动效制作。

统一风格是制作要求；源库没有硬编码只能漫画风。风格与渲染方式也可分别选择。

选择二 · 哪些交给模型，哪些自己控制

人物表演 + 本地场景编排

模型先生成单独的人物表演，本地代码制作背景、文字、镜头与合成。人物姿态仍需与计划中的场景匹配。

当前证据：已实测 5 秒 H3 表演、抠像和全曲插入。

“抽卡”程度取决于生成范围与约束：完整场景可以先由一张接受的构图约束；分层人物也可能出现姿态或口型失误。参考图、表演视频、局部修改和明确的时间轴，可以减少交给模型自由决定的内容，不能保证每次生成都可直接使用。

方案 A · 分层，姿态先匹配

坐姿人物 + 对应的车厢布景

先确定一张完整构图：座位、桌面、人物朝向、景别与光线。然后制作同机位的无人车厢背景，以及基于同一身份的单姿态坐姿关键帧。

让 H3 从这个坐姿关键帧演唱，保持下半身姿态与镜头稳定。合成时对齐身体位置和桌面接触点：椅背在人物后面，桌沿 / 扶手按需要在人物前面，接触阴影跟随姿态安排。

杯子若由人物拿着，可跟人物一起生成；独立桌子与扶手需要场景图层和遮罩。背景和人物的透视、光线或姿态不一致时，仅调 x、y、缩放无法全部补救。

方案 B · 物理互动镜头的例外

用完整场景关键帧生成这个镜头

对于“坐着靠椅背、手肘压桌面、手拿杯子”这样的接触镜头，可以把接受的完整构图作为视频参考，让模型在同一个镜头里生成场景与人物表演，再审查口型、手部和家具稳定性。

源库明确允许少数必须与物体互动的短镜头使用完整场景 H3，要求简单环境、少量道具、固定机位和短时长。分层是它的默认路线，这个镜头可以因接触关系而采用例外。

这是一条拟验证路线，尚未用我们的 API 跑过。它减少了手工拼接接触关系的工作，也把家具和背景的稳定性交给模型，需要查看真实输出再决定是否采用。

对这支歌曲的具体设计：可以保留列车静态图作为统一构图参考，先选定一个露出嘴部的坐姿演唱镜头。需要复现桌椅与手部接触时，考虑一个短的完整场景镜头；其他演唱特写与动态排版继续分层。当前正面 H3 只适合另一个近景镜头，不应直接冒充这张图里的坐姿表演。

05 / ALPHA MATTING

绿幕只负责分离人物，RGBA 让人物进入可控的场景。

原库：绿占优势 → Alpha → 去绿

cutout.py 逐帧读取 RGB，测量绿色比红、蓝强多少，再映射成 Alpha。它不是用视频模型重画一遍人物。

dom = G - max(R, B)
alpha = clip(255 - (dom - 25) * 6, 0, 255)

alpha → MinFilter(3) → GaussianBlur(0.8)
G_clean = min(G, max(R, B) + 10)

output: 0000.png … + metadata.json

强绿色趋向透明，非绿色保留；最小值滤波略收边，模糊让边缘柔和，去绿减少反光。算法会受绿色衣物、半透明头发、阴影影响，必须查看 Alpha 与不同背景上的边缘。

源库另有纸色抠像：从边界 flood fill 找背景，再按 seed 保留人物连通分量。浅色皮肤或衣料更适合绿幕；纸色路线并不是本次使用的算法。

完整抠像源码

我们：FFmpeg chromakey + despill

实际背景取样约 #008E3C，与提示词中的 #00B140 有差异。因此使用实际颜色调整参数，而非照搬文字描述。

format=yuva444p,
chromakey=0x008E3C:0.12:0.05,
despill=type=green:mix=0.5:expand=0.2:
        green=-1:red=0.15

这里的 similarity / blend 控制颜色容差与透明过渡；它与源库“绿色优势”公式是两种实现。输出透明 QTRLE / ARGB MOV，保留人物原帧，再叠到背景上。

07 / WHY IT LOOKS NATURAL

自然感来自表演、风格与编排同时成立。

源库把质量控制放在每个边界

  • 同一身份参考经过审查后锁定，再制作单姿态关键帧。
  • 表演同时包含嘴、下巴、眉眼、肩膀与动作前后衔接，按真实唱词与停顿安排。
  • 人物材质、背景、字体和图形服从同一风格；镜头与画面事件跟随歌词和音乐。
  • 先检查素材，再检查段落播放，最后检查整曲与结尾；失败素材不自动向后扩散。

以上是源码中的制作要求。我们没有逐项复现原样片的完整制作记录，不能断言某一张参考图、某一个阈值就是原样片自然感的唯一原因。

我们的试验只验证了一小段链路

  • 480P 正面近景，人物细节与机位丰富度有限；原库默认 1080P。
  • 直接使用原混音，没有人声分离、逐句听音修订和完整词级时刻。
  • 背景只用了现有窗景；p5 场景编排、动效排版与 Swift 特效尚未移植。
  • 仅 5 秒有真实演唱；其余 122 秒左右仍是图片镜头版。

浏览器自动化目前无法启动，完整播放和逐字口型复核尚未完成。静帧、帧数与音频指标是已有证据，不足以宣布达到原作者整曲的表演质量。

mouth_sync.py 是检测辅助，不是口型模型。

脚本统计嘴部 ROI 中的暗像素比例，近似表示张嘴程度；同时计算每帧人声能量，在 −6 到 +6 帧的偏移中寻找相关性。24fps 下，这是约 ±250ms 的粗略时差检查。

它没有把音频变成 /p/、/m/、/a/ 等音素，也没有生成逐帧嘴形，更没有改动人物视频。张嘴跟音量相关不等于发音准确；移动的人脸、低对比嘴部与伴奏串音会让结果不可靠。原库明确要求继续听看音素、嘴形和停顿。
