1. 定位：组织设计工作的流程与工具包

Huashu Design 把任务说明、设计规范、参考风格、起手组件、导出脚本和检查方法放在一起。模型负责理解资料与写代码，浏览器负责显示页面，格式转换工具负责生成文件。

它本身没有训练新模型，也没有提供现成的完整业务平台。其主要增量是把通用 Agent 也能组合使用的能力组织起来，减少临时查规范、搭展示外壳和拼导出步骤的工作。本轮没有做使用前后的效率对照，不能量化“快了多少”或证明“设计一定更好”。

2. “主要是初步目标”需要按交付目的区分

对于软件产品，原型可以验证页面、流程与部分前端交互。本次搜索、收藏、本地保存和下载确实工作，但账户、权限、数据库和协作服务仍需工程实现。

对于演讲、归档和视频介绍，HTML 演讲稿、PDF、PPTX、MP4 本身就可能是最终交付物。是否完成，取决于内容、排版、编辑要求及使用环境是否通过验收，不能用“都是原型”概括所有产物。

4. 共同底层与实际差别

共同流程是：提供事实材料，确定受众与目的，编写 HTML/CSS/JavaScript，浏览器渲染，再选择目标格式。

但多个输出不是无条件互转。交互原型需要事件和状态；可编辑 PPT 要求受约束的页面结构与固定尺寸；视频需要由统一时间驱动画面。越早明确交付目标，越容易选择合适的实现路线。不能先随意做一个复杂网页，再默认它能无损转换为所有格式。

5. 已验证、未验证与需要另建的部分

  • 基础成果检查：83 项通过，见真实场景报告。后续阅读器和内容导航检查另记，不混同为上游新增能力。

  • 需要独立工程：身份、业务数据存储、协作、权限、部署、持续维护。

本次“研选”的内容、界面与业务交互由当前任务编写，组件和导出工具复用上游。运行完整 Skill 与取用其中的组件/脚本是不同的验证范围。

6. 真实使用中暴露的问题

Windows 文件路径、浏览器启动方式和录制视口需要适配。PPT 转换器需要从页面编写阶段遵守约束；导出包装中的无目标母版声明也需要清理。文件生成成功之后，仍要检查页数、中文、对象编辑能力、图像、播放与目标软件表现。

这些问题说明接入成本应计入判断。本项目保留原始上游源码、适配列表和验证记录，详见 真实场景报告。

7. 对当前研究工作的意义

最直接的用法是把现有研究资料转成可讲解、可讨论、可留档的成果。先用原型讨论流程，再用演讲稿交流结论，按需要交付 PDF、可编辑 PPT 或视频。

如果日常只需要简单文字笔记，增加视觉制作步骤未必合算。如果经常重复制作类似汇报，品牌规则、章节结构、资料来源与验收条件更值得沉淀。若目标是研究平台，采用这个工具包后仍要另建业务系统。

8. 扩展顺序与采用判断

先扩充内容模板和品牌规范，再抽取常用组件，然后按需要接企业 PPT 模板、数据源或新的导出器。自动化任务队列、多人工作空间和管理后台属于产品工程，不是补几段提示词就得到的能力。

下一次试用可以选择自己确实要交付的材料，记录内容错误、返工次数、修改成本、目标软件兼容性与总用时，再决定是否纳入长期流程。已有本次效果展示，可作为起点；它还不是通用质量基准。

5. 六种目标为什么需要不同适配

原型需要浏览器状态、表单和交互，采用响应式布局。PPT 则必须从页面编写之初遵守转换器约束：1280×720 固定画布，文字放在 p/h 标签，装饰放在外层，不使用 CSS 渐变或 background-image。否则“已有网页直接转 PPT”容易失败。

六页汇报的文本源只维护一份，由生成器写出独立 HTML 和 deck-stage 内容。PDF 与 PPTX 都来自这组页面。浏览器演讲适合导航，PDF 固定阅读，PPTX 便于继续编辑，三者不保留原型的业务交互。

视频并非录制鼠标操作。四个镜头使用真实原型截图和预设光标运动，所有过渡都由 Stage 的统一时间驱动。MP4 渲染器向页面传入 t = 帧序号 / 30，等待布局稳定后截图，再编码。它展示的是操作流程的表达方式，不是假装已经操纵后台。

7. 实际遇到的兼容问题

  1. 上游脚本用字符串拼接 file:// 路径。在 Windows 下改用 pathToFileURL，并对 PPT 图片路径使用 fileURLToPath 解码。
  2. 上游默认启动 Playwright 自带 Chromium；本机使用已安装 Chrome，显式传入 executablePath。没有修改全局浏览器配置。
  3. Stage 即使隐藏控件仍扣除 56px 高度，录制会出现不必要留白。编译副本仅在 __recording 模式停止扣除；正常浏览仍保留控件区域。
  4. 上游 PPT 导出允许部分页面失败后仍交付。这里改为任一页失败即退出，避免把缺页文件交给用户。
  5. 导出包装声明了 slideMaster2 到 slideMaster6，但文件内只有实际使用的母版。独立结构检查发现后，移除 5 个无目标的 Content Types 声明。先确认没有关系引用它们，修复未改变任何幻灯片或备注 XML。尚未隔离出该现象来自上游调用方式还是本机 pptxgenjs 版本，因此不归咎于其中某一方。
  6. 中文字体采用本机 Microsoft YaHei。PDF 实际渲染通过；PPT 在其他软件/机器上仍可能因字体度量而改变换行。

前端和导出适配清单逐条列出源字符串、替换字符串与理由；文件包装修复记录随验证 JSON 一并提供。

4.1 文档驱动的任务路由

不同任务会加载不同资料。例如品牌任务取得真实 logo 与产品素材；幻灯片先选择页面组织与输出；动画读分镜、镜头和后端约定；长解说读音频时间轴路线。按需加载降低无关上下文，但每个宿主仍需具备相应读写、执行和浏览器能力。

4.2 品牌资产固化

将 logo、产品图、UI、字体、配色和禁区整理为 brand-spec.md，让多个页面共用同一份上下文。它减少凭记忆猜品牌的情况，但自动取得素材不等于完成真实性与授权核验；高频色值也不一定是品牌主色。资产协议

4.3 HTML 作为通用中间产物

浏览器已有成熟的字体、排版、图形、事件和可编程测量能力。模型能够生成代码，开发工具能够版本化保存，因此 HTML 很适合连接内容表达、交互与媒体输出。代价是格式转换存在语义差异：网页流式布局不等于 PPT 的固定坐标，视频不能保留原型行为。

4.4 动画：时间映射为视觉属性

animations.jsx 的 Stage 管全局时间，Sprite 管片段局部进度，interpolate 与 Easing 计算位置、大小和透明度。普通播放采用 requestAnimationFrame；seek 模式由外部 __seek(t) 指定时间。第 n 帧对应 t=n/fps，只要同一时间产生同一画面，就可以确定性渲染。独立 CSS keyframes、随机数和第二套时钟需要适配。动画组件、逐帧脚本

新项目默认 HyperFrames，使用暂停的 GSAP 时间轴逐帧定位，并提供 3D、shader、透明通道的扩展入口。弱环境、既有 Stage 项目、纯交互与长解说另有路线。复杂能力来自外部框架及适配，不能认为自研 Stage 已内置专业三维系统。后端边界

4.5 PPT：测量并重新表达对象

路线 A 的 html2pptx.js 实际启动 Chromium，读取位置、尺寸与 computedStyle，再用 pptxgenjs 写对象；要求输入结构符合约束。路线 B 的 pptx_from_rendered.py 使用渲染后的元素结果和 python-pptx，可继承已有母版，SVG/canvas 以图片进入 PPT。

因此，路线 B 文档“路线 A 只读源码”的说法与当前源码不符。两者都依赖浏览器，真正区别是结构校验、元素映射、输出库与模板支持。A 源码、B 源码

4.6 解说：先测音频，再排画面

narrate-pipeline.mjs 解析带 scene 和 cue 的 Markdown，分段调用 TTS，用音频真实时长形成 timeline.json，并拼接 voiceover.mp3。可用时保留字级时间戳；失败时降级，不保证卡拉 OK 字幕。画面和字幕通过 NarrationStage 使用统一时间轴。管线源码

调节面板只改变预先暴露的属性，状态写入 localStorage。它使颜色、字号、密度便于比较，但不是任意编辑器，也不会把选择自动写回源码或同步到他人设备。调参配方

2. HTML 原型与演讲稿

HTML 是可修改源文件，交互在浏览器运行。原型的状态切换不等于真实接口；需要明确标注模拟内容。默认复杂 deck 以多文件加概览组织，单文件用于更简单或共享状态的场景。主文档对单文件页数有不同表述，实际按内容与壳的约束选择。

验收：关键路径、首尾翻页、概览点击、刷新状态、图片加载、浏览器错误、窄屏与投屏字号。若交付离线文件，需确认所有远程字体、脚本和图像的处理方式。

3. PDF

多文件路线使用 Playwright 为每页 HTML 打印 PDF，再用 pdf-lib 合并；单文件 deck-stage 有专用脚本以处理页面组织。文件名排序决定多文件页序，应采用补零编号。

node scripts/export_deck_pdf.mjs --slides slides --out deck.pdf --width 1920 --height 1080

字体和文本通常可以保留可搜索形式，位图图片仍然是位图。不能简单承诺“零视觉损失”或“所有内容矢量”。复杂浏览器效果、字体未加载和打印尺寸都要检查。

验收：页数与顺序、标题正文、文字可搜索性、图片分辨率、分页裁切、链接和预期打印尺寸。

来源：PDF 脚本。

4. PPTX 两路线

A：从零规划

html2pptx.js 通过真实浏览器测量 DOM，再转为可编辑 PPT 对象。输入结构需符合文本标签、容器装饰、图片与尺寸等约束。比如某些 CSS 渐变、背景图或结构组合无法直接进入输出，必须在设计阶段选择支持的表达。

尺寸按物理单位理解：默认推荐的 960pt × 540pt 对应 13.333 × 7.5 英寸，而不是把 HTML 像素越设越大就能提高 PPT 质量。

B：已有视觉稿或企业模板

python scripts/pptx_from_rendered.py deck.html -o deck.pptx --selector ".slide"
python scripts/pptx_from_rendered.py deck.html -o deck.pptx --template company-template.pptx --layout "内页" --skip-class logo

该路线可从现有模板开始，保留母版、主题与版式。让 logo 等公共元素由母版提供，避免在页面内容层重复绘制。画布尺寸以模板为准，脚本按比例映射。

SVG/canvas 在该实现中截图为图片；图片圆角可被烘焙进透明通道。文本、简单形状可编辑不意味着复杂图表数据与节点全部可编辑，也不保留网页交互。

PPT 必须单独验收

  • 在最终使用的 PowerPoint/WPS 打开，不能只看缩略图。
  • 逐页核对文字、图像、字体、行距、换行和层叠。
  • 修改一处文本和一处母版元素，验证编辑体验。
  • 对比源内容与 PPT 文本、图片数量，发现遗漏。
  • 准备已知正确模板作为对照，先确认渲染工具没有字体问题。

来源：A 约束、B 指南。

6. 解说与音频

解说稿以 scene 与 cue 组织，TTS 生成分段音频，ffprobe 等工具测量时长，再写 timeline.json。NarrationStage 使用时间轴组织画面与字幕，最后混入人声、背景音乐和动作音效。

7. 图片、SVG 与透明素材

PNG 的清晰度取决于像素尺寸；印刷“300dpi”需要把最终物理尺寸与像素数对应起来。修改 DPI 元数据不会创造更多细节。SVG 适合原生矢量图形，不能假设整页任意 HTML 都能自动变成可编辑 SVG。

透明 MOV/WebM/PNG 序列属于 HyperFrames 后端文档提供的路线。验收时把素材叠在彩色背景上看边缘和阴影，并确认目标剪辑软件支持的编码。本轮未实测。

4. 接入真实数据

建议把数据获取与视觉生成分开。先产生一个经过校验的中间结构，再让设计使用它。例如为每组指标保存 value、unit、period、source、updatedAt；出现空值时显式展示“暂无数据”，不要自动填充好看的数字。

动态仪表盘还需要接口、缓存、认证与错误状态。这些属于扩展工程；信息图脚本本身不提供完整的数据平台。

5. 接企业 PPT 模板

优先检查目标模板的页面尺寸、母版与版式名称，让公共 logo 留在母版层。先用两页代表内容验证文本和图表，再批量生成。生成后实际修改母版确认其他页面跟随变化；也要检查文字、字号和行距。

避免同时混用两条转换路线带来的不同对象与尺寸策略。路线选择见 导出指南。

6. 替换语音或视频服务

新 TTS 适配器至少要明确输入文本、音色与速度，输出音频、总时长及可选字级时间戳。保留文本规范化差异与失败降级，例如服务把数字读成另一种表达时，字幕不能机械地按原字符对齐。

替换视频后端时，先约定唯一时间源、画布尺寸、素材加载完成信号、首帧状态与音轨。使用三个最小基准：文字进出、跨镜头连续元素、字幕与人声同步。不要直接从长片开始验证。

7. 增强质量而非堆更多规则

  • 把常见失败变成可重复检测的问题：缺文字、错单位、溢出、按钮无动作、音轨缺失。
  • 验证工具本身：用已知正确和已知错误的样例各测一次。
  • 为主观判断保留截图与解释，避免只输出总分。
  • 比较新旧结果时固定模型、资料、尺寸、输出要求和预算。
  • 记录返工原因，修改最影响结果的规范或组件。

8. 如果要做团队平台，还缺什么

需要额外建设任务入口、身份权限、素材归属、文件版本、队列与重试、并发资源限制、模型/服务费用统计、成果审核和分享方式。若执行任意生成代码，还要设计运行隔离。上游库适合作为其中的规则与媒体工具层，不是现成完整系统。

9. 保持可升级

固定使用的 commit，保存自身变更说明。尽量把品牌与业务模板放在独立目录；修改上游核心文件时留下差异。升级前对比路由与脚本契约，运行代表性原型、PPT 和动画回归，不把最新版本直接视为稳定版本。

10. 对本研究仓库的优先建议

  1. 固定一套“开源项目研究”内容字段：定位、输入输出、模块、运行、边界、来源。
  2. 用同一事实材料生成网页版解释、讲解 deck 和架构图，各自独立验收。
  3. 保存有价值的交互教学组件，例如时间轴、状态机、参数对比与路由选择。
  4. 将证据等级和验证记录作为所有新研究的必备字段。
  5. 只有重复出现的视频或 PPT 需求，才值得继续投入自动导出与批量工具。
